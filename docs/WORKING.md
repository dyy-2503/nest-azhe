# 我们的合作方式

（2026-11-22 用户定义，按此执行）

## 三个阶段

### 阶段一（现在）
用户下发任务 → 我执行 → 汇报结果。

### 阶段二（下一步）
我**主动推断缺什么** → 列出候选和理由 → **问用户** → 得到同意 → 动手。

### 阶段三（最终）
我推断 → **自己做** → 做完通知用户，不需要事前同意。

### 什么时候可以进阶段三
用户说了算。默认策略：阶段二跑顺几轮、我没有踩过"自作主张做错"的坑，就由用户宣布进入阶段三。

## 阶段三也仍然要问的事（不可逆 / 影响外部）

这几类即使进了阶段三也要先问：

- **删数据**：删会话、删账号、清库、删媒体文件
- **动别人的东西**：其他用户的数据、别人的 AI 人设
- **对外发布**：推到远端仓库、公开发布、装到别人机器上
- **花钱**：买域名/证书/云服务
- **改这台机器的全局设置**：开机自启项、系统代理、防火墙规则

其余（加功能、改 UI、修 bug、写文档、跑测试、加脚本）都属于"自己做完通知"。

## 汇报格式（阶段三的"通知"）

1. 我判断缺什么、为什么
2. 做了什么、怎么验证的（数字/截图/日志）
3. 还剩什么没做、卡在哪
4. 需要用户做的事（如果有）

### 1. 从本地世界切回服务器世界（明天优先）
现象：手机 App 切到 `http://127.0.0.1:8787`（本地世界）之后，回不到 PC 服务器。
排查方向：
- 「服务器」按钮在本地服务器页面里是否还挂载（`isInAppShell()` 依赖 Capacitor 桥注入，
  非允许源页面可能不注入桥；兜底是 `https://localhost/icon.png` 探测）
- 点击后 `https://localhost/index.html?switch=1` 是否被 Capacitor 拦掉（混合内容/allowNavigation）
- 壳页面 `?switch=1` 分支是否真的清掉 KEY_LAST 并停在地址页
验收：本地世界 → 点「服务器」→ 地址页 → 填 PC 地址 → 能回到 PC 世界；反向也能切回。
